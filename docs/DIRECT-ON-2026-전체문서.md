Overview

### 한눈에 보기

무엇을 만들고, 무엇을 제출하고, 무엇으로 평가받는지 정리했습니다.

고객의 음성 문의를 실시간으로 듣고, 기업의 응대 매뉴얼에 맞춰 정확하게 응답하며, 필요한 업무는 함수 호출로 처리하는 음성 AI 상담원 서버를 구현합니다.

#### 만들 것

- WebSocket 기반 실시간 음성 AI 상담원
- 고객 음성 입력 → 음성 응답
- STT, LLM, Function Calling, TTS를 연결한 서버
- 함수 호출을 받는 간단한 모의 함수 서버

#### 제출할 것

- 실행 가능한 프로토타입
- 서버 소스 코드

- 최종 기획서
- 최종 발표자료

#### 평가받는 것

- 사용자 경험 50점
- 응답 품질 및 기능 구현 20점
- 발표 및 질의응답 20점
- 최종 기획서 10점

이 과제의 핵심은 **속도 × 정확성 × 자연스러운 고객 경험**의 균형입니다. 시스템 점수만 높여서는 좋은 평가를 받기 어렵습니다. 실제 고객이 쓰고 싶은 상담원을 어떻게 설계했는지가 평가의 중심입니다.

## 2. 문제

원문: https://direct-on.vercel.app/problem.html

DIRECT:ON 2026 · 11.21

Challenge

빠르고 정확한 쇼핑몰 음성 상담 AI

Real-Time Voice AI Customer Service

건강기능식품 쇼핑몰의 전화 고객 상담을 AI로 자동화하는 것이 이번 DIRECT:ON의 기업 과제입니다.

고객이 전화로 문의하면, AI가 고객의 요구를 이해하고 필요한 정보를 확인한 뒤 정확하고 자연스러운 음성으로 응대해야 합니다.

단순히 질문에 대답하는 챗봇이 아니라, 실제 고객 상담 업무를 수행하는 AI 상담원을 만들어야 합니다.

Background

### 문제 배경

#### 반복되는 고객 문의, 그러나 매번 다른 상황

쇼핑몰 고객센터에는 배송 조회, 주문 취소, 반품·환불, 상품 문의 등 비슷한 상담이 반복됩니다.

하지만 전화 상담은 상담원이 한 명씩 직접 응대해야 하므로, 문의가 몰리면 대기 시간이 길어지고 상담원의 업무 부담도 증가합니다.

AI가 이러한 업무를 대신하려면 단순히 고객의 말을 알아듣는 것만으로는 부족합니다. 전화 상담에는 세 가지 어려움이 있습니다.

#### ① 기다려주지 않는 고객

전화에서는 2~3초만 침묵이 이어져도 고객이 통화가 끊긴 것으로 느낄 수 있습니다. 정확한 답변을 준비하는 동시에 빠르게 반응해야 합니다.

#### ② 불완전하고 복잡한 음성 정보

고객은 주문번호를 잘못 말하거나, 말을 정정하거나, 이전 대화의 맥락을 생략할 수 있습니다.

예를 들어 “공일공”과 “영일영”처럼 같은 숫자도 다르게 표현될 수 있어 음성 인식 오류에 대응해야 합니다.

#### ③ 정확해야 하는 실제 업무 처리

주문 조회나 환불 접수처럼 실제 업무와 연결되는 상황에서는 작은 실수가 잘못된 처리로 이어질 수 있습니다.

확인되지 않은 정보를 임의로 안내하거나, 필요한 정보를 받기 전에 업무를 실행해서는 안 됩니다.

Business Scope

### 대상 상담 업무

이번 과제에서 다루는 업무는 건강기능식품 쇼핑몰의 전화 고객 상담입니다.

| 상담 유형 | 주요 업무 |
| --- | --- |
| 배송 | 주문 상태 및 배송 현황 확인 |
| 주문 취소 | 취소 가능 여부 확인 및 처리 |
| 반품·환불 | 반품 접수, 환불 절차 및 진행 상태 안내 |
| 교환 | 상품 교환 문의 및 접수 |
| 결제 | 결제 수단, 입금 및 결제 관련 문의 |
| 상품 | 제품 정보, 가격, 이용 방법 안내 |
| 상담원 연결 | AI가 해결하기 어려운 문의의 인계 |

각 업무에는 서로 다른 확인 절차와 응대 정책이 존재합니다. 참가팀은 고객의 문의를 올바르게 분류하고, 필요한 정보를 수집한 뒤 적절한 방식으로 응대해야 합니다.

Core Challenges

### 핵심 해결 과제

#### Challenge 1. 얼마나 빠르게 반응할 것인가?

고객의 발화가 끝났는지 판단하고, 가능한 한 빠르게 첫 음성을 출력해야 합니다. 기존 기업 과제의 속도 목표는 **첫 응답 1.5초 이내**입니다.

다만 단순히 “잠시만 기다려주세요”라는 말을 빠르게 반복하는 것이 좋은 상담 경험을 의미하지는 않습니다. 빠르게 응답하면서도 실제로 고객의 문제를 해결하는 방법을 고민해야 합니다.

#### Challenge 2. 얼마나 정확하게 처리할 것인가?

AI는 고객이 말한 전화번호와 주문번호를 정확하게 인식하고, 필요한 경우 적절한 업무 기능을 호출해야 합니다.

빠른 응답을 위해 필수 확인 절차를 생략하거나, 잘못된 정보를 안내해서는 안 됩니다.

#### Challenge 3. 어디까지 AI가 처리해야 하는가?

모든 고객 문의를 AI가 끝까지 처리해야 하는 것은 아닙니다. 특정 업무에서는 추가 확인이 필요하고, 일부 상황에서는 사람 상담원의 판단이 더 적절할 수 있습니다.

어떤 업무를 자동화하고, 언제 사람에게 인계할 것인지도 중요한 설계 문제입니다.

Your Mission

### 여러분이 해결할 문제

이번 과제에서 여러분은 다음 질문에 대한 답을 찾아야 합니다.

- **Q1.** 고객의 말을 얼마나 빠르고 정확하게 이해할 수 있는가?
- **Q2.** 기업의 응대 절차와 정책을 지키면서 실제 고객 요청을 처리할 수 있는가?
- **Q3.** AI 모델, 시스템 구조, 함수 호출 방식을 어떻게 조합해야 더 좋은 상담 경험을 만들 수 있는가?
- **Q4.** AI가 처리할 업무와 사람 상담원이 처리할 업무를 어떤 기준으로 구분할 것인가?

정해진 하나의 기술이나 아키텍처가 정답인 것은 아닙니다. 각 팀이 선택한 해결 방식과 그 판단의 근거가 이번 과제의 중요한 차별점이 됩니다.

Scope

### 구현 범위

아래 파이프라인 전체를 하나의 서버로 구현합니다. LLM이 호출할 모의 함수 서버도 팀이 직접 만듭니다.

고객 음성 입력 참가자가 구현하는 서버 (WebSocket) STT LLM TTS 음성 응답 출력 모의 함수 서버 (직접 구현) Function Calling

좌우로 밀어 전체 구조를 볼 수 있습니다.

| 구성 요소 | 구현할 일 |
| --- | --- |
| WebSocket | 음성 입력을 받아 음성 응답을 돌려주는 실시간 서버. 입력부터 응답까지 끊김 없이 이어져야 합니다. |
| STT | 고객 음성을 텍스트로 변환합니다. |
| LLM | 응대 매뉴얼에 맞춰 대화를 이해하고 응답을 만듭니다. |
| Function Calling | 업무 처리가 필요하면 모의 함수 서버의 함수를 호출하고 결과를 응답에 반영합니다. |
| TTS | 응답 텍스트를 음성으로 변환해 고객에게 돌려줍니다. |
| 모의 함수 서버 | LLM의 함수 호출을 받는 간단한 mock 서비스입니다. 들어온 입력에 맞는 기록을 주어진 데이터에서 찾아, 정해진 출력을 그대로 돌려줍니다. |

#### 모의 함수 서버

실제 업무 시스템을 만들 필요는 없습니다. 함수 호출이 들어오면 주어진 데이터에서 입력에 맞는 기록을 찾아 정해진 출력을 돌려주는 수준이면 충분합니다. 평가의 초점은 함수 서버의 내부 구현이 아니라, 상담원이 **필요한 순간에 올바른 함수를 올바른 인자로 호출하고, 돌려받은 결과를 응답에 자연스럽게 반영하는가**입니다.

골격은 `mock_tools/` 폴더에 있고, 입력에 맞는 출력을 골라 돌려주는 `lookup()`을 팀이 채웁니다. 다른 언어로 새로 만들어도 됩니다. 모의 함수 서버는 아래 두 경로를 제공합니다.

| 경로 | 역할 |
| --- | --- |
| `GET /tools` | 사용할 수 있는 함수 목록과 정의를 돌려줍니다. 제공되는 함수 정의와 같아야 합니다. |
| `POST /tools/{name}` | JSON 입력을 받아 정해진 JSON 출력을 돌려줍니다. 정의에 없는 함수는 거부합니다. |

응답할 데이터는 실행할 때 파일로 받습니다. 연습 때는 연습용 모의 함수 데이터를, 최종 측정 때는 운영진이 측정 직전에 건네는 시험용 데이터를 읽어 다시 띄웁니다. 응답 규칙은 11/21에 공개되는 규격 문서를 따릅니다.

#### 측정기의 함수 중계

측정기는 상담원 서버와 모의 함수 서버 사이에 **함수 중계**를 둡니다. 상담원 서버가 받는 `tools_url`은 이 중계의 주소이고, 중계가 호출을 모의 함수 서버로 넘긴 뒤 응답을 그대로 돌려줍니다. **함수 호출 기록과 함수별 응답 지연은 중계가 맡으므로** 모의 함수 서버는 맞는 결과만 돌려주면 됩니다.

함수를 부를 때는 `tools_url`로 받은 주소를 그대로 쓰고, **`X-Session-Id` 헤더에 `session.start`로 받은 세션 ID를 반드시 넣습니다.** 이 헤더가 빠진 호출은 채점에서 호출하지 않은 것으로 봅니다. 모의 함수 서버 주소를 코드에 고정해 두면 최종 측정에서 호출이 기록되지 않습니다.

구성 요소 외에, AI가 처리할 범위와 Human Handoff 기준, 속도와 품질 사이의 trade-off는 팀이 직접 정하고 근거를 남겨야 합니다.

응대 매뉴얼, 브랜드 정보, 함수 정의, 연습 문항과 손님 음성, 연습용 모의 함수 데이터, 측정기·채점기는 11/21 현장 공개입니다. 평가에 쓰는 시험 문항은 끝까지 공개하지 않습니다. 사전에는 사전 공개 스타터킷(예시 서버, 연습용 측정기, 모의 함수 서버 골격, 가상 음성 3개)으로 통신과 함수 호출 흐름을 미리 연습합니다.

### 준수사항

- **제공 자료의 안내를 따릅니다.** 스타터킷의 예시 서버와 연습용 측정기 사용법은 스타터킷 `README.md`에 있습니다. 11/21에 공개하는 공식 자료의 사용 방법은 그 자료의 문서와 현장 안내를 따릅니다.
- **스타터킷은 연습용입니다.** 스타터킷의 함수, 고객 발화, 주문번호는 공식 문제와 다를 수 있고, 스타터킷으로 얻은 점수는 공식 점수가 아닙니다.
- **응대 매뉴얼과 브랜드 정보를 따릅니다.** 매뉴얼에 없는 정책을 지어내거나, 손님에게 받아야 할 정보를 받지 않고 함수를 호출하거나, 사람 상담원에게 넘겨야 할 상황에서 AI가 계속 응대해서는 안 됩니다.
- **모의 함수 서버는 팀이 직접 만듭니다.** 입력에 맞는 정해진 출력을 돌려주는 간단한 mock 서비스로 구현하며, 실제 업무 처리 로직은 만들지 않아도 됩니다. 함수를 호출할 때는 `tools_url` 주소로 부르고 `X-Session-Id` 헤더를 반드시 넣습니다.
- **시스템 평가는 운영진이 직접 측정합니다.** 행사 당일 오후, 운영진 노트북의 측정기가 비공개 시험 문항으로 각 팀 서버에 접속해 측정·채점합니다. 팀은 같은 측정기·채점기로 연습 문항 점수를 미리 확인할 수 있습니다.
- **측정 시간에는 두 서버를 켜 둡니다.** 상담원 서버와 모의 함수 서버를 자기 노트북이나 클라우드에서 띄우고, 운영진이 접속할 두 주소를 알려 줍니다. 운영진은 서버를 제공하지 않습니다. 측정은 문항 4개가 동시에 들어오므로 동시 접속을 처리해야 하고, 측정 중에는 서버를 고치거나 다시 띄우지 않습니다.
- **제공 데이터는 대회 안에서만 씁니다.** 제공 데이터는 실제 상담 기록의 개인정보를 가짜 값으로 바꾼 것으로, 밖으로 옮기거나 공개하지 않습니다. 측정 중 사람이 대신 답하는 것, 시험 문항 음성을 저장하거나 빼내는 것, 측정기 동작을 우회하는 것은 실격 사유입니다.
- **시스템 점수만을 위한 설계를 지양합니다.** 모든 응답을 “잠시만 기다려주세요” 같은 채움말로 시작해 시스템 점수만 높이는 방식은 실제 고객 경험 측면에서 좋은 설계로 보지 않을 수 있습니다.
- **Human Handoff 기준을 직접 정의합니다.** AI가 처리하지 않을 문의와 사람 상담원에게 연결하는 조건을 기획서와 발표에서 설명할 수 있어야 합니다.
- **직접 만든 시스템을 설명할 수 있어야 합니다.** 처리 순서와 응대 방식을 정한 이유, 개발 중 겪은 문제를 질의응답에서 기술적 근거를 들어 답할 수 있어야 합니다.

#### 실시간 STT 접속 예제

Soniox 실시간 STT는 WebSocket으로 접속합니다. 아래 내용은 Soniox 공식 문서 기준입니다(11/20 확인).

- 주소는 `wss://stt-rt.soniox.com/transcribe-websocket`입니다. API 키는 연결할 때 `Authorization: Bearer 키` 헤더로 보냅니다.
- 연결 직후 설정 JSON을 먼저 보내고, 이어서 음성을 바이너리 프레임으로 보냅니다. 측정기가 보내는 16kHz · 16-bit · mono PCM은 `pcm_s16le`로 지정하면 변환 없이 그대로 보낼 수 있습니다.
- `enable_endpoint_detection`을 켜면 Soniox가 말이 끝났다고 판단할 때 `<end>` 토큰을 보냅니다. 발화 종료 감지에 쓸 수 있습니다.
- 빈 텍스트 프레임(`""`)을 보내면 스트림이 끝나고, 마지막 응답에 `"finished": true`가 옵니다.

```python
import asyncio, json, os, websockets

URL = "wss://stt-rt.soniox.com/transcribe-websocket"

async def transcribe(chunks):  # chunks: 16kHz 16-bit mono PCM 조각
    headers = {"Authorization": f"Bearer {os.environ['SONIOX_API_KEY']}"}
    async with websockets.connect(URL, additional_headers=headers) as ws:
        await ws.send(json.dumps({
            "model": "stt-rt-v6",
            "audio_format": "pcm_s16le",
            "sample_rate": 16000,
            "num_channels": 1,
            "language_hints": ["ko"],
            "enable_endpoint_detection": True,
        }))

        async def send_audio():
            async for chunk in chunks:
                await ws.send(chunk)      # 바이너리 프레임
            await ws.send("")             # 빈 텍스트 프레임 = 스트림 종료

        sender = asyncio.create_task(send_audio())
        text = ""
        async for msg in ws:
            res = json.loads(msg)
            for t in res.get("tokens", []):
                if t["text"] == "<end>":   # 말이 끝남
                    print("발화 종료:", text)
                elif t["is_final"]:
                    text += t["text"]
            if res.get("finished"):
                break
        await sender
```

#### 통신 규격

측정기는 아래 순서로 상담원 서버와 통신합니다. 스타터킷과 11/21 공식 자료의 순서는 같으며, 세부 규격은 공식 자료의 규격 문서를 따릅니다.

- 문항 하나가 연결 하나입니다. 연결 직후 JSON 텍스트 메시지 `session.start`가 먼저 옵니다. 세션 ID, 현재 시각, 이번 말 이전까지의 대화 이력, 발신자 정보, 함수를 부를 주소(`tools_url`)가 들어 있습니다.
- 이어서 고객 음성이 16kHz · 16-bit · mono PCM 바이너리로, 20ms(640바이트) 단위로 실제 말하는 속도에 맞춰 들어옵니다.
- 고객이 말을 마친 뒤에도 무음 조각이 계속 들어옵니다. **말이 끝났는지는 팀이 직접 판단**해야 합니다. 말 중간에 1초 넘게 쉬는 고객도 있습니다.
- 응답 음성은 같은 형식의 PCM 바이너리로 보내고, 응답을 마치면 `{"type":"turn.end"}` 텍스트 메시지를 반드시 보냅니다. 함수를 호출했다면 결과를 받아 답한 뒤에 보냅니다.
- 고객이 말을 마치기 전에 응답 음성을 보내면 끼어든 것으로 처리됩니다. 고객 말이 끝나고 25초 안에 `turn.end`가 오지 않으면 측정기가 연결을 끊습니다.

실제 고객이 AI 상담원을 사용한다고 가정했을 때의 경험을 심사위원이 정성적으로 평가합니다. 빠른 응답보다 실제 고객에게 좋은 상담 경험을 제공하는지가 중요합니다. 세부 기준은 [사용자 경험 평가 기준](https://direct-on.vercel.app/eval.html#ux)에서 확인할 수 있습니다.

#### 응답 품질 및 기능 구현 · 20점

행사 당일 오후, 운영진이 비공개 시험 문항으로 각 팀 서버를 직접 측정·채점합니다. 시스템 점수는 **응대 50% + 함수 20% + 속도 30%**로 계산하고, 100점 만점의 시스템 총점을 5로 나눠 20점 항목에 반영합니다.

| 시스템 점수 | 비중 | 평가 내용 |
| --- | --- | --- |
| 응대 점수 | 50% | 응대 매뉴얼에 맞게, 가격·정책·절차·조회 결과 등 사실을 틀리지 않고 응대했는가. 문항마다 맞음 1.0 / 괜찮음 0.7 / 틀림 0으로 판정합니다. |
| 함수 점수 | 20% | 손님 기록을 조회하거나 바꾸는 함수를 맞는 때에 맞는 전화번호·주문번호로 호출했는가. 호출하면 안 될 때 호출해도 틀립니다. |
| 속도 점수 | 30% | 고객 말이 끝난 뒤 첫 소리까지의 시간. 함수를 호출한 문항은 조회 결과를 받은 뒤 실제 답까지의 시간도 함께 봅니다. |
| 합계 | 100% | 시스템 총점 ÷ 5 = 20점 항목 점수 |

##### 속도 점수표

| 응답 시간 | 점수 |
| --- | --- |
| 1.5초 이하 | 100 |
| 2.0초 이하 | 90 |
| 2.5초 이하 | 80 |
| 3.0초 이하 | 70 |
| 3.5초 이하 | 60 |
| 4.0초 이하 | 50 |
| 5.0초 이하 | 30 |
| 6.0초 이하 | 10 |
| 6.0초 초과 | 0 |

- “확인해 보겠습니다” 같은 채움말도 첫 소리로 인정합니다. 다만 함수를 호출한 문항은 첫 소리 점수와 조회 뒤 답 점수의 평균이 속도 점수이므로, 조회 뒤 답이 늦으면 점수가 깎입니다.
- 소리를 내지 않거나, 연결에 실패하거나, 고객이 말하는 도중에 첫 소리를 내면 그 문항의 속도 점수는 0점입니다.
- 연습 때는 같은 측정기·채점기로 연습 문항 점수를 미리 볼 수 있습니다. 채점기는 받아쓰기와 채점에 OpenAI API를 쓰므로 키가 필요합니다.

#### 발표 및 질의응답 · 20점

- 시스템 구조를 왜 이렇게 설계했는가
- 같은 모델에서 왜 이 처리 순서와 응대 방식을 선택했고, 개선 전후에 무엇이 달라졌는가
- 어디까지 AI가 처리하도록 했는가
- 어떤 경우 사람 상담원에게 연결하도록 설계했는가
- 속도와 응대 품질 사이의 trade-off를 어떻게 판단했는가
- 실제 개발 과정에서 어떤 문제가 있었고 어떻게 개선했는가
- 심사위원 질문에 기술적 판단 근거를 설명할 수 있는가

#### 최종 기획서 · 10점

문제 정의, 핵심 사용자, 주요 기능, 사용자 흐름, 기술 스택, 시스템 아키텍처, 데이터 흐름, AI 처리 범위, Human Handoff 기준, 주요 기술적 의사결정, 중간 피드백 반영 내용을 중심으로 평가합니다.

Experience

### 사용자 경험 평가 기준

심사위원은 다음 요소를 중심으로 봅니다.

- 불필요한 말을 반복하지 않는가
- 고객의 요구를 정확하게 파악하는가
- 응답 속도가 실제 대화에서 자연스러운가
- 고객이 말하는 도중에 개입하거나 추가 질문을 했을 때 대응할 수 있는가
- 응답이 간결하고 명료한가
- 고객이 원하는 업무가 자연스럽게 완료되는가

#### 감점으로 이어질 수 있는 사례

| 사례 | 고객이 겪는 문제 |
| --- | --- |
| 필요 이상으로 긴 답변 | 음성 대화에서는 긴 답변을 끝까지 듣기 어렵습니다. |
| 모든 답변에 동일한 채움말 반복 | 고객은 같은 말을 계속 듣게 됩니다. |
| 이미 전달된 정보를 다시 묻는 경우 | 대화 맥락을 기억하지 못하는 상담원으로 느껴집니다. |
| 고객의 핵심 요구를 놓치는 경우 | 정확한 답이어도 고객이 원한 답이 아니면 업무가 끝나지 않습니다. |
| 고객의 중간 개입을 무시하는 경우 | 고객의 정정이나 추가 질문이 반영되지 않습니다. |
| 지나치게 빠르지만 부자연스러운 응답 | 고객이 말을 마치기 전에 답하거나 대화 리듬이 어색해집니다. |
| 정확하지만 응답 시간이 지나치게 긴 경우 | 침묵이 길어지면 고객이 통화가 끊겼다고 오해할 수 있습니다. |

시스템 점수를 높이는 것만으로는 부족합니다. **속도 × 정확성 × 자연스러운 고객 경험** 사이의 균형을 팀이 직접 설계하고, 발표에서 그 근거를 설명해야 합니다.

### 최종 제출물

제출물은 네 가지이고, 시스템 평가는 운영진이 직접 측정합니다.

| 최종 발표자료 | Problem & Goal, System Architecture, AI Scope & Human Handoff, Speed vs. Quality, Demo, Evaluation Result, Failure / Improvement |

GenerativeLab이 중점적으로 확인하는 것은 두 가지입니다.

① 평가 지표에 해당하는 **실제 수치**: 운영진이 측정한 시스템 점수로 확인합니다. 팀이 연습 문항으로 잰 수치는 발표의 Evaluation Result에 담습니다.
② 시스템 구조를 그렇게 설계한 **방식과 이유**: 최종 기획서와 발표에 담습니다.

#### 시스템 측정 진행

1. 측정 시간 전에 상담원 서버와 모의 함수 서버를 띄우고, 운영진에게 두 주소를 알려 줍니다. 같은 행사장 네트워크라면 노트북 IP를, 접속이 막히면 터널 주소를 알려 줍니다.
2. 측정 직전에 운영진이 시험용 모의 함수 데이터 파일을 건넵니다. 모의 함수 서버를 이 파일로 다시 띄웁니다.
3. 운영진 측정기가 비공개 시험 문항의 고객 음성을 팀 상담원 서버로 보냅니다. 상담원 서버는 `tools_url`(운영진 측정기의 함수 중계 주소)로 나가는 연결이 되어야 합니다.
4. 측정이 끝나면 운영진이 채점해 스코어보드를 만듭니다. 측정 중에는 서버를 고치거나 다시 띄우지 않습니다.
